## Highlight carry-forward on framing re-export (T4350 + T4355)

The problem: `working_videos.highlights_data` is the SOLE home of user overlay-edited highlights (`transform_all_regions_to_raw` has ZERO production callers → edits are never written to raw space). A framing re-export creates a NEW `working_videos` version; the live finalizers used to seed it from FRESH detection → the prior version's edits were **silently discarded**.

- **Decision site (single chokepoint): `upsert_working_video` (`export_finalize.py`), INSERT branch ONLY.** It reads the prior wv (`highlights_data` + `framing_snapshot`) via `projects.working_video_id` BEFORE the repoint, then calls `services/highlight_carry.resolve_carried_highlights(prior_highlights, prior_snapshot, new_snapshot, detected_regions, clip_count)`. The **UPDATE/resume branch sets only filename/duration/detections_data** — it must NOT touch `highlights_data`/`framing_snapshot`/`highlight_carry_note`, or a recovery-after-sync-failure re-run re-seeds detection over the carried regions (the original bug, on the recovery path).
- **Decision matrix** (`highlight_carry.py`): empty prior → seed detected; `prior_snapshot == new_snapshot` → verbatim fast-path; prior_snapshot is None (legacy, ANY clip_count) → verbatim carry + `"legacy_uncertain"` (promoted above the clip_count split — carrying real regions with a "verify positions" flag beats a detection reset); `clip_count == 1` + differs → `_transform_single_clip` (`to_raw`(old framing)→`to_working`(new framing), drop out-of-range), `note="dropped:N"`; `clip_count > 1` + differs → **`_transform_multi_clip`** (T4355, below), same `dropped:N` contract; residual unmappable multi-clip → detected + `"multiclip_reset"`. Transform preserves region metadata (merge geometry onto the original by id); `dropped` counts ENABLED regions only.
- **T4355 — multi-clip per-region attribution + transform (closes Gap B).** Highlight regions live in CONCATENATED working-video seconds with no clip reference. `_attribute_clip_index(start_time, offsets, durations)` buckets each region into its OLD clip via a **half-open span** `[off_i, off_i+dur_i)` — attribution is by `start_time` alone (a region's geometry is authored against the moment it begins); an exactly-on-boundary `start_time` attributes to the LATER clip, never the earlier one. `_transform_multi_clip` then: shifts the region into that clip's LOCAL old timeline (clamping `end_time` to the clip's OLD span end for a straddling region — mirrors the single-clip transform's existing partial-trim clamp) → runs the SAME `transform_all_regions_to_raw`/`_to_working` pair against `clips[i]` (generalizing `_transform_single_clip`'s hard-indexed `clips[0]`) → re-offsets into the clip's position on the NEW concatenated timeline → id-merges geometry back onto the original region. DROP+count (folded into the same `dropped:N`, never a new note) when: the attributed OLD clip index no longer exists on the NEW side (removed, or reordered past the new count), the straddle-clamp collapses to sub-frame, or the per-clip transform returns nothing (trimmed out on the NEW side).
  - **Clip identity is POSITIONAL ONLY** (`clips[i]`, no stable id in the snapshot) — a true clip reorder is indistinguishable from "the clip at this position got reframed." A region on a reordered clip safely DROPS+flags (never silently lands on the wrong clip's timeline); true reorder-survival would need a persisted clip id and is a follow-up, not attempted here.
  - **Dissolve transitions:** `_build_framing_snapshot` gained an additive `"transition":{"type","duration"}|None` key (no migration, same BLOB) so a re-export's OLD-side concat offsets can subtract the dissolve overlap. `concat_offsets(snapshot)` (`routers/export/multi_clip.py`) is the shared cumulative-offset formula (`get_output_duration` per clip + dissolve subtraction), used for BOTH old and new sides — **kept independent from**, not merged into, the pre-existing `build_clip_boundaries_from_durations`/`_from_input` (those consume raw `ClipExportData`/measured durations for detection boundaries; `concat_offsets` consumes the snapshot's canonical `{segments_data, raw_duration}` — different input shapes bounded the abstract-on-3rd extraction; the dissolve-subtraction LOOP is duplicated across three sites and must be kept in sync by hand if either changes). Absent/`None` `"transition"` ⇒ treated as **cut** (never guesses dissolve) — this is what lets a LEGACY prior snapshot (written by T4350 before this key existed) still transform correctly on a plain cut re-export.
  - **Landmine (caught in Reviewer, fixed before merge):** the "can't derive OLD offsets" unmappable-guard must key on the **NEW-side** transition (`_dissolve_offsets_unavailable(prior_snapshot, new_snapshot)`), not "OLD snapshot lacks a `transition` key" alone. An OLD-only guard resets **every** legacy multi-clip project — including plain cut re-exports — on its very next re-export, discarding real user highlights the design explicitly says should transform fine. `NOTE_MULTICLIP_RESET` now fires ONLY when the prior snapshot lacks `transition` **and** the current export's own NEW side is itself a dissolve (the one case where the OLD overlap is genuinely unknowable).
- **Framing snapshot** (`{clip_count, video_dims, clips:[{crop_keyframes(FRAME-based), segments_data(canonical), fps=30, raw_duration}], transition:{type,duration}|None}`): built at export START in `_export_clips._build_framing_snapshot` from the render's own `ClipExportData` (frame-based crop captured before the render's time-based conversion — `interpolate_crop_at_frame` needs frame-based), NOT re-read at finalize (avoids the pre-export-PUT race). Threaded via `job input_data` + `_persist_rendered_checkpoint` so recovery reconstructs it. `video_dims` = render target resolution. `transition` key added T4355, additive/optional.

## Cross-profile game references (T5800, profile_db v030)
- A **reference game** is a `games` row with `source_profile_id IS NOT NULL` (+ `source_game_id`,
  both nullable, profile_db **v030**). It is a **metadata-only link** to a game owned by a SIBLING
  profile of the same user, materialized so a MOVED reel (T5810) keeps its by-game grouping in the
  target profile's Gallery. Referenceness is DERIVED (`source_profile_id IS NOT NULL`), there is NO
  `is_reference` boolean (EPIC decision 3). Metadata is FROZEN at materialization (name/opponent/
  date/type/tournament/dims/durations + `created_at` copied from source; a later rename of the
  owning game does NOT propagate).
- **What a reference row is NOT:** it has **no `game_storage` row, no Postgres `game_storage_refs`,
  no `game_ref_counts`** (EPIC decision 4 — video lifecycle stays 100% with the owning profile).
  So `list_games` (`games.py:_read_games_for_list`/`_list_games_impl`) **skips ALL storage-expiry
  computation for references** — a reference emits `storage_status=None`, `storage_expires_at=None`,
  `can_extend=False`, plus `is_reference=true`/`source_profile_id`/`source_game_id`/`source_profile_name`
  (owning profile's display name from `user_db.get_profiles`, ONE read, no N+1). `source_game_id` lets
  the frontend (T5820) locate the owning game by exact id match — including MULTI-VIDEO owning games,
  whose `blake3_hash` is NULL and so could never be used as a matching key. Athlete stats are naturally
  zero (no local `raw_clips`). NEVER show an expiry chip on a reference card.
- **Primitive:** `materialization.ensure_game_reference(target_conn, target_profile_id,
  source_profile_id, source_game_row, source_game_videos) -> int` (the 2nd cross-profile game
  copier; shares the insert with `_copy_game` via `_insert_game_with_videos`). 4-step resolution:
  (1) dedup on `(source_profile_id, source_game_id)`; (2) chain-collapse — a reference SOURCE
  resolves through its own source pointer so references never point at references (EPIC dec. 6);
  (3) hash-dedup against a REAL local game (share-materialized earlier) via
  `_find_existing_game_by_hashes` → reuse it, no reference; (4) else insert a reference. Takes an
  ALREADY-OPEN target conn (Row factory); callers own cross-profile DB opening + R2 sync ordering.
- **Migration-window (v030):** `source_profile_id`/`source_game_id` land on the bootstrap-hot games
  SELECT, so `_read_games_for_list` `column_exists`-guards them (projects `NULL` on a pre-v030 DB —
