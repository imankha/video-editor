Per-gesture autosave for the play editor

The mechanism for removing the Save/Update button (EPIC D1–D8) — create at the tap, one write per field, ordered delivery, delete instead of cancel.

The play editor is currently a submit-form hiding inside an autosave app: nine fields collected locally, one handleSave payload on click. This design routes every field through the seam ClipDetailsEditor.jsx already proved out — one gesture, one field, one PUT — and answers the three things that needed real design before code: how a play comes to exist without a Save click, how two editors converge on one text-commit pattern, and how out-of-order writes get an ordering guarantee without a version counter.

What changed in v2

A second review verified v1’s load-bearing claims against the code. Four were wrong in ways that would have shipped races; three were smaller consistency gaps. All seven are now in the doc, each with a pinning test.

01Create POST queued as chain head — the editor opens before the POST resolves (addClipRegion :1281 is sync, await saveClip :1317 is not), so an early trim would have POSTed a duplicate rowblocking
02rawClipIdByRegionRef written synchronously — setRawClipId is React state, not fresh by the next microtask; v1’s “closed by construction” claim was notblocking
03Failure tracked per payload key, Retry routes through the queue — v1 let a successful rating tap clear a failed trim, so Frame navigated on stale bounds (the exact D4 case)major
04Delete queued behind pending writes — otherwise a DELETE can beat a name PUT, the PUT 404s, and a Retry toast appears for a play that no longer existsmajor
05Clean-check on every commit, in one place — onDragEnd fires on every pointer-up whether the handle moved or not; a no-op tap cost a durable PUT + R2 round tripminor
06One Escape rule — v1 had Escape mean “abandon” in the strip’s inline name field but “save and close” in the form bodyminor
07Sidebar “(auto)” label reads isDefaultPlayName — every play now carries “Play N” as a real name, so a has_custom_name-derived flag would never show it againminor

A. The state machine collapses

Today a play doesn’t exist until Save, so the editor needs a CREATING state for a row that isn’t there yet. Once Mark Play creates the row at the tap, the editor only ever opens on something real — CREATING loses its only producer.

Before — 4 states

  • 01 NONE — no selection
  • 02 SELECTED — clip highlighted
  • 03 EDITING — overlay open, existing clip
  • 04 CREATING — overlay open, no clip yet
→

After — 3 states

  • 01 NONE — unchanged
  • 02 SELECTED — unchanged
  • 03 EDITING — the only editor state; reached from the T10310 row, the toolbar, or the create tap
  • — CREATING — deleted, no producer remains

C. Ordering without a version counter

Independent per-field writes can race — a trim released a beat before Frame is tapped, or a beat after Mark play while the create POST is still in flight. A per-region promise chain (modelled on actionClient.js’s FIFO, no version threading) serializes everything that touches the same region: the create is the head, field writes chain behind it, Retry re-enqueues, Delete is the tail. Frame waits for the tail to settle.

Mark play→ enqueue(A, create)→ POST /save
drag‑end (POST still in flight)→ enqueue(A, trim)→ waits for id→ PUT {startTime,endTime}
tap Frame, 100ms later→ awaitRegionWrites(A)→ tail settles→ navigate
Failure is tracked per field: a failed trim stays failed until a trim write lands, no matter how many rating taps succeed in between. A rejected tail leaves the Retry toast up and the CTA does not navigate — no new dialog; Retry goes back through the same queue, so a real fix clears it. Chaining + a synchronously written rawClipId map (not React state, which isn’t fresh by the next microtask) closes the stale‑closure race annotate.md’s T9630 entry flagged as open.

Open questions

The fullscreen toolbar’s “Add play (A)” while already editing

Q1

Under create‑at‑tap this becomes a no‑op while an editor is already open. Should it instead close the current one and start a second play?

✓ Recommendation: no‑op. A silent close‑and‑create is more surprising than doing nothing.

“Play saved” toast on every tap

Q2

It now fires once per Mark Play tap. Does that get chatty for someone marking several plays in a row?

✓ Recommendation: keep it. It’s the only confirmation the row exists at all — revisit with real usage data.

Does Done resume playback?

Q3

handleOverlayResume (close + resume) loses its only caller. Should Done also un‑pause, or just close?

✓ Recommendation: just close. Matches the explicit entry/exit direction from T10400; the user presses play themselves.

Save‑status scope

Q4

Should the saving/saved/error badge track per‑region state, or one global flag for whichever editor is open?

✓ Recommendation: global‑per‑editor. Only one editor is ever open at a time — matches today’s saveStatus shape.
