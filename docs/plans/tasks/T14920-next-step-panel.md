# T14920: "Next Step" panel: what to do next, the tasks that move it, and the roadmap in the admin UI

**Status:** WIP
**Impact:** 8
**Complexity:** 5
**Tier:** L (new pattern: roadmap data inside the app; design gate on the data source)
**Created:** 2026-11-03
**Updated:** 2026-11-05

User request 2026-11-03: "can we create a 'Next Step' Panel that basically tells me what I need to
do next and the roadmap for UI?"

## Problem

The admin shows numbers (Journey map, pulse cards, and after T14900 / T14910 their colours), but
nothing says what to do about them. The owner wants one place that answers three questions in
order: what is the biggest leak right now, which planned tasks move it and which one is next, and
whether paid spend is allowed yet. The roadmap that answers the second question already exists in
PLAN.md (the 2026-11-03 ranking table maps each Journey stage to the tasks that move it, in order),
but it is not visible from the app.

## Solution

A "Next Step" panel at the top of the admin Journey tab, above the Spend readiness panel, with four
parts:

1. **Biggest leak.** The transition with the largest absolute loss among those T14900 colours red or
   yellow, with its rate, target and loss count ("Opened upload -> Footage landed: 66%, target 78%,
   100 lost"). Ties break by funnel order (earlier stage first), the same rule PLAN.md uses.
2. **Do next.** The ordered tasks mapped to that stage, each as id, title, status chip (TODO / WIP /
   WAITING ON USER / STAGING) and a link to the task file on GitHub. The first non-STAGING task is
   highlighted as "Next". If every mapped task is STAGING or absent, say "nothing planned for this
   stage" loudly rather than hiding the row.
3. **Spend verdict.** T14910's `verdict.line` (approved design 2026-11-05: two verdicts, the
   measurement flight and channel economics, with settled / provisional confidence), its `focus`
   (tier and worst gate), and the tasks the stage map assigns to that gate's key (for example
   `visit_to_signup` -> T7410, `upload_failure` -> T9000, `finished_to_took_away` -> T14840). The
   panel prints the verdict line as T14910 composes it; it never recomputes a verdict.
4. **Roadmap.** The whole stage -> tasks table as a compact list grouped by stage in funnel order,
   each task with its status chip, collapsed by default. This is the PLAN.md ranking table rendered,
   not a second roadmap.

### Where the roadmap data comes from (design gate; recommendation below)

PLAN.md is the only source of truth for task order and status. The app must not keep a second
status store. Two options for the architect:

- **A (recommended): build-time export.** `scripts/export_roadmap.py` parses PLAN.md's Current
  Focus tables (id, title, status, section) and a small stage map (which section or task moves which
  Journey stage and which spend gate) into `src/frontend/src/components/admin/roadmap.json`,
  generated by the frontend build (`npm run build` step and the dev server), never committed by
  hand. The panel prints "roadmap as of <build time, commit>". Statuses are as fresh as the last
  deploy, which is the same freshness as everything else in the admin.
- **B: hand-maintained constants** `roadmapStageMap.js` with a Vitest test that every id exists in
  PLAN.md. Rejected unless A proves too heavy: it rots the day someone updates PLAN.md without the
  constants.

Either way the stage map keys use the frozen Journey stage keys (T14720) and the gate keys from
T14910's constants module, so a renamed label never breaks the mapping. A path no CI rule claims
fails the `changes` job; add a `ci_policy.py` rule naming the frontend build as the consumer of the
script and the stage map (no fan-out).

### Rendering

- Mobile-safe (admin is sometimes opened on a phone): one column, chips wrap, roadmap collapsed.
- Status chips reuse the task board's colours so the two tools agree.
- No animation beyond the existing admin transitions; respect reduced motion.

### Technical Notes
- Read only; nothing persists; no gesture writes.
- "Biggest leak" uses absolute loss (users), not rate, because that is how PLAN.md orders sections;
  the panel and the plan must agree or the owner gets two answers.
- If roadmap.json is missing at runtime, render a loud "roadmap export missing" row, never an empty
  panel (no silent fallback).
- Link target for a task is its file on the repo's default branch; no in-app task editing.
