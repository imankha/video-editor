T10690: true "unset" rating state (nullable raw_clips.rating)

Design gate · WAITING ON USER · 2026-09-19 · Full design: docs/plans/tasks/T10690-design.md
Already settled, not re-litigated here: a true nullable rating, chosen over a session-only "touched" flag, knowing it reverses part of T10610 which merged today. This is a domain widening, not a data fix. Every existing rating is a real 1 to 5 star value; nothing is backfilled and nothing is rewritten. The migration only changes what the column permits.
Good news from the audit: the backend was already written defensively against a missing rating. glicko.seed_rating(None) already returns a neutral seed ("no silent star guess"), collection_metadata already carries quality_score = None, auto_export already filters rating IS NOT NULL, and Focus mode's clip sidebar already tests clip.rating != null. The real work is the migration, the Annotate surfaces, and removing nine || DEFAULT coercions.

A. Schema change

The column

-- src/backend/app/database.py:1182  (profile_db track, PRAGMA user_version)
  CREATE TABLE raw_clips (
    id        INTEGER PRIMARY KEY AUTOINCREMENT,
    filename  TEXT NOT NULL,
-   rating    INTEGER NOT NULL,
+   rating    INTEGER,            -- NULL = no rating on record (T10690, v054)
    ...
  )

SQLite cannot ALTER COLUMN ... DROP NOT NULL, and there is no table-rebuild precedent in migrations/profile_db/: all 53 existing ones are ADD COLUMN or DROP COLUMN. New file v054_raw_clips_rating_nullable.py follows SQLite's official 12-step procedure. Four traps it must handle, each one silent data loss if missed:

TrapWhy it bitesHandling
FK cascade on DROP TABLE Three tables reference raw_clips(id) ON DELETE CASCADE (working_clips, modal_tasks, clip_teammates). With foreign_keys=ON, dropping the old table is an implicit DELETE FROM and would delete every working clip in the profile. PRAGMA foreign_keys=OFF around the rebuild (set outside a transaction, where it is not a no-op), plus foreign_key_check before commit. Never rely on the caller's default: two openers use ON.
Indexes die with the table idx_raw_clips_game_id, idx_raw_clips_rating, and the UNIQUE idx_raw_clips_game_end_time_seq (the game-cut natural key). Capture their sql from sqlite_master before the drop, replay verbatim after the rename.
sqlite_sequence reset The AUTOINCREMENT counter is deleted with the table. If any clip was ever deleted, new ids reuse old ones, and final_videos.source_clip_id (T3630 ranking) holds frozen raw-clip ids with no cascade, so a published reel would silently re-point at a different play. Read seq before the drop, restore MAX(old, new) after.
Partial crash This is the first profile_db migration that commits inside up(). A crash before the runner stamps user_version = 54 leaves a nullable column at v053. The "already nullable, return" guard makes a re-run a no-op. Harmless by construction.

No backfill. Existing 1..5 values copy across byte-identical. The migration runs itself just-in-time at each profile's next access (JIT seam), so there is no operator step.

Recommended

A. Reuse the UNDONE treatment

amber dashed ring, hollow star, copy "Not rated yet"
  • Zero new visual state. rated: false already routes to UNDONE, and the disc already shows a star outline with no notation. The only edits are the predicate and the copy.
  • Honest: the row then reads "three things you haven't done yet", which is what it is.
  • Worth weighing: the premise that the other badges "default to something" does not quite hold. An unnamed play has no custom name, an un-noted play has no note. Same shape as unrated.
  • Risk: three amber badges on every fresh play may feel naggy on a 30-play game.
Alternative

B. Its own UNSET state

same amber hue, lower emphasis: border-amber-500/50, text-amber-300/70, no fill
  • Says "optional, not pending". Visually recessive next to the two action badges.
  • Stays in the amber family, so it never reads disabled.
  • Costs: one enum member, one class row, one mapping change (about 6 LOC) plus a test.
  • Risk: at 44px the difference from UNDONE is subtle and may read as an accident.
Not recommended

C. Gray or neutral

dashed slate ring, gray star
  • Maximum separation from the "to do" badges, but:
  • T10440 already reverted gray on these exact badges because "gray read as disabled". Re-introducing it on the one badge the user is meant to tap first re-runs that regression.
  • It also collides with DORMANT (dotted gray) on the clip badge.

In every option the disc shows a hollow star and no notation glyph (notation exists only for 1 to 5), no check mark, and the picker opens with no row selected. That last part is already true, since aria-checked={rating === value} is false for all five rows when the rating is null.

C2. Can a rating be cleared back to unset?

Recommended

No. Unset is only reachable before the first rating

  • rating stays a 1..5 int on every write: one code path, no absent-vs-explicit-null ambiguity.
  • "I rated it and now want it unrated" is a rare need, and the value is always changeable.
  • Consequence to accept: the unset visual is a first-time-only affordance.
If you want it

Yes. A "No rating yet" row in the picker

  • One extra picker row calling the same onRatingChange(null) setter. It is a real tap, so the gesture-persistence rule holds with no new write path.
  • Requires clips.py:1499 to switch from if update.rating is not None to if 'rating' in update.model_fields_set. The model uses None to mean "absent" for all ten fields, so clearing is currently inexpressible.
  • About 10 LOC plus a test. A dedicated /clear-rating endpoint was considered and rejected (a second write path for one field).
