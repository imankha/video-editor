### Acceptance criteria — evidence
1. **"Novice can see intended moving output before paid export"**: satisfied by slice 3's
   `[Preview highlight]` toggle — re-frames the SAME playing video to the output aspect via
   `contentTransform`, so pressing play during preview shows the moving crop-filled output before
   any render. Verified by `outputPreviewTransform.test.js`'s "fills the box" / letterboxed-source
   cases and `FocusModeView.framingActionRow.test.jsx`'s toggle test; NOT verified in a real
   browser (see gap above).
2. **"Preview/export crop, timing, format and audio decisions agree; approximation is disclosed"**:
   crop is the SAME `currentCropState` the reticule/renderer use (no second crop value); timing
   (trim/speed) and audio (`muted={!includeAudio}`) were already unchanged by this task per the
   design doc's architecture analysis (§1.2) — preview is literally the same `<video>` playing.
   Format = `globalAspectRatio`, same value the stage box and the export use. Disclosure line
   (`EDITOR_PANELS.PREVIEW_DISCLOSURE`/`PREVIEW_MULTI_CLIP_DISCLOSURE`) renders only while
   previewing, verified by `FramingActionRow.test.jsx`. Image-quality/multi-clip-concatenation
   approximation is disclosed per the design doc's exact copy, not asserted against a real export.
3. **"Advanced controls remain available without dominating first use"**: slice 1's
   `advancedOpen` disclosure, default collapsed for fresh clips / open for clips with existing
   splits/trim (R4). Verified by `FocusModeView.advancedEditing.test.jsx` and
   `FocusTimeline.test.jsx`.
4. **"Wider framing is reversible, persists and retains source bounds"**: reversible via
   session-scoped `[Undo]` (exact restore, `useFramingHistory.test.js`) and via the toggle-off
   (returns to the default crop size at the same center, `widenFraming.test.js`); persists through
   the existing surgical crop-keyframe write path (no new write path, `FocusContainer.jsx`);
   retains source bounds via `resizeAboutCenter`'s clamp into `[0,0,videoW,videoH]` plus the
   existing `clampCropForCurrentRotation` layered on top for straightened clips
   (`widenFraming.test.js`'s rotation-safe-area-clamp case). NOT verified against a live reload
   round-trip in a real browser (same environment gap as above).
