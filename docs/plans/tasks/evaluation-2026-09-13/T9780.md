## Outcome record

- **Status and verified remaining scope:** implemented as a one-file additive frontend
  bug fix (branch `feature/T9780-fix-spotlight-fromdetection-restore`). The task brief's
  proposed design (revision-bound export-job dispatch + validated-artifact promotion) was
  investigated and found **unnecessary** — see the two "investigated, not needed" items
  below. No remaining product scope; the evaluator observation is explained and fixed.

- **Root cause:** `restoreRegions` in
  `src/frontend/src/modes/overlay/hooks/useHighlightRegions.js` rebuilt each restored
  keyframe with an explicit key whitelist (`frame, x, y, radiusX, radiusY, strokeOpacity,
  fillOpacity, color`) that silently dropped `kf.fromDetection`. `fromDetection` is the
  **sole** field marking a keyframe as a real player assignment —
  `src/frontend/src/modes/overlay/utils/detectionAssignment.js` `isDetectionAssigned`
  treats a boundary keyframe lacking it as unassigned scaffolding. So every reload or
  Overlay remount (including an Overlay -> Focus -> Overlay round trip with no page
  reload) rebuilt regions through `restoreRegions` and stripped the marker. Then
  `OverlayModeView`'s `awaitingPlayerSelection` check (built from
  `countDetectionAssignments`) saw zero assigned detections and re-showed "Pick your
  player", and suppressed the tracking-ellipse overlay — even though the DB still held
  correct x/y/radius geometry for the assignment. **Purely a read/restore-path bug: the
  DB data was never corrupted, it was misread back into memory.**

- **Relationship to T9770 / T9700:** this is the **frontend twin of T9770** (PR #428,
  backend `add_keyframe` UPDATE-branch fix in `routers/overlay.py`, which set
  `fromDetection` on an existing keyframe matched within tolerance). T9770 fixed the
  UPDATE branch; the CREATE / first-save path already persists `fromDetection` correctly
  server-side. This bug lives entirely in how the frontend reconstructs its in-memory
  shape FROM that correct DB data — a DIFFERENT bug than T9700/T9770 checked: no prior
  work round-tripped `fromDetection` through the frontend restore path.

- **Changed implementation paths / commit:** commit `b6f333da`.
  - `src/frontend/src/modes/overlay/hooks/useHighlightRegions.js` — `restoreRegions`
    keyframe map now carries `...(kf.fromDetection ? { fromDetection: true } : {})`
    additively (never fabricates the marker on a keyframe that never had one — mirrors
    T9770's own rule). No backend change, no migration, no schema change.
  - `src/frontend/src/modes/overlay/hooks/useHighlightRegions.persistence.test.js` — two
    new tests (see below).

- **Investigated, NOT needed (out of scope — no build):**
  1. **Job/revision binding & artifact promotion.**
     `insert_export_job_if_none_active` (`src/backend/app/services/export_helpers.py:79`)
     is an atomic per-`(project_id, type)` compare-and-set
     (`INSERT ... SELECT ... WHERE NOT EXISTS ... status IN ('pending','processing')`
     under the per-user SQLite write lock) that 409s a second concurrent dispatch, making
     out-of-order overlay completions structurally impossible. `_finalize_overlay_export`
     (`src/backend/app/routers/export/overlay.py:121`, swap at lines 245-247) INSERTs the
     new `final_videos` row and only then `UPDATE projects SET final_video_id = ?` — and
     this shared completion path runs solely on SUCCESS (a failed render calls
     `fail_export_job`, never this). So a failed/cancelled render cannot advance playable
     state and an out-of-order job cannot replace a newer result. Building revision-bound
     promotion on top of this existing guard would be a defensive fix for an internal bug
     that cannot occur (CLAUDE.md: "no defensive fixes for internal bugs").
  2. **"No ellipse visible in sampled frames" (brief screenshots E38/E43).** Not a render
     defect. The auto Spotlight region spans only the first ~2.0s
     (`DEFAULT_HIGHLIGHT_REGION_DURATION`, `routers/export/multi_clip.py`), and the T5250
     reveal envelope (`services/spotlight_reveal.py` / `utils/spotlightReveal.js`) ramps
     opacity from 0 at the region's start/end boundaries (opacity = 0 exactly at
     start/end; both factors = 1.0 only mid-region). A frame captured "near the start"
     (the evaluator's caption) is EXPECTED to show nothing; mid-region (t~=1.0s) shows the
     full ellipse. No renderer patch warranted.
