# T8520 + T8530 UI spec: completion choice card + draft preview player

**Author:** ui-designer pass
**Date:** 2026-09-03
**Status:** proposal, awaiting user approval (4 decisions flagged D1-D4)
**Scope:** two connected surfaces
1. T8520's post-Focus-export completion choice card
2. T8530's draft preview mode in `CollectionPlayer` (the user's locked
   "preview before publish" decision, superseding the task file's Option A/B)

Everything below is grounded in current source; file:line references are what I read,
not what the task files claim.

---

## 0. Read this first: a mechanism the task files get wrong

**A Focus (framing) export does NOT produce a shareable reel.** It produces a WORKING
video only. The final video, which is the only publishable/shareable artifact, is
created exclusively by the OVERLAY export.

Evidence:

| Fact | Source |
|------|--------|
| Framing export inserts into `working_videos`, updates `projects.working_video_id`, and never touches `final_videos` | `src/backend/app/routers/export/framing.py:259-269` (docstring at :179-194 lists the same 6 steps) |
| `final_videos` rows are inserted only by the overlay export | `src/backend/app/routers/export/overlay.py:236`, `:1930` |
| A draft counts as complete only via `has_final_video` | `src/frontend/src/components/DraftTile.jsx:355-356`; `src/frontend/src/utils/draftStage.js:52` |
| Publish reads the latest `final_videos` row and 404s when there is none | `src/backend/app/routers/downloads.py:2119-2133` |
| The Overlay screen's render CTA is literally labeled "Add Spotlight" | `src/frontend/src/modes/OverlayModeView.jsx:40, 273, 618` |

Consequences for the two task files:

- T8520's proposed secondary button copy, "Skip - my reel is ready", is **false** at
  that moment. Nothing is ready. Skipping leaves the draft at stage
  `DRAFT_STAGE.IN_OVERLAY` ("Draft - in Overlay"), with no final video, nothing to
  preview in a player, and nothing to publish or share.
- The user's locked decision ("T8520's Skip button navigates to the same preview
  surface") cannot be honored literally: at Skip time there is no reel to preview.
- The product hole this exposes is real and is the actual root of cliff 4: **the app
  has no button that means "finish my reel".** The only button that renders the final
  video is called "Add Spotlight", so a user who does not want a spotlight has no
  path to a finished reel at all.

This forces decision **D1** below. Everything else in this spec is written to work
under either D1 branch; only the choice card's copy and its X/Escape semantics change.

## 2. D1 (BLOCKING): what does the second choice on the card actually do?

Because a Focus export yields no final video, "Skip" has to mean one of these.

### Option A (RECOMMENDED): Skip means "finish my reel now"

The card's secondary action starts the final render immediately and the user lands on
the draft preview player when it completes, exactly like the "Add a spotlight" path.

Implementation with the smallest diff: Skip does what today's code already does
(`setEditorMode('overlay')`) and additionally fires the overlay export through the
existing `exportButtonRef` mechanism (`App.jsx:567-568`). Every downstream path stays
byte-identical: same progress UI, same WebSocket completion, same
`handleExportComplete` routing, and therefore the same landing on the preview player
that T8530 builds. No new export plumbing, no backend change, no credit charge
(overlay exports skip the credit check).

- Pro: the sentence "my reel is ready" becomes true; both branches converge on ONE
  completion surface; it fills the real product hole (no button today means "finish").
- Con: the user briefly sees the Overlay screen (dominated by render progress) after
  choosing not to add a spotlight. Mitigated by copy ("Finishing your reel...").
- Con: T8520's e2e path B now involves a real render. Assert that the render STARTED
  (progress visible) rather than waiting for completion; T8530's own e2e covers the
  landing.

### Option B: Skip is navigation only

Skip goes home and the draft sits at "Draft - in Overlay". Copy must then be honest:
"Later" or "Not now", never "my reel is ready". The preview surface is unreachable
from this card, so T8520 and T8530 no longer share a destination at all.

- Pro: zero new behavior, smallest possible change.
- Con: leaves the user exactly where cliff 4 already leaves them, one undisclosed step
  short of a reel, which is what this epic exists to remove.

### Option C (rejected): promote the working video to a final video on skip

A backend change that would make "framing export = finished reel" true. Rejected: the
overlay render also owns poster capture, intro attachment, name freezing, and the
final-video versioning. Duplicating that path is out of scope and would create a second
source of truth for "a finished reel".

**Recommendation: Option A.** The rest of this spec assumes A and notes the two places
B changes things.

## 3. Surface 1: the completion choice card (T8520)

### Placement and shell

Rendered from `FocusScreen.jsx` in place of the current `setEditorMode('overlay')` at
`:1023-1025`, driven by local state `showExportCompleteChoice`. Persist nothing.

Use the existing `ConfirmationDialog` primitive rather than a bespoke card. It already
carries the exact contract this moment needs: `fixed inset-0` centering that ignores
the Focus screen's scroll position, `max-w-md w-full mx-4` (358px at 390px viewport),
no backdrop close, Escape to `onClose`, and an X in the header. It needs the two small
fixes listed in section 1 (mobile stacking, optional button icon).

```jsx
<ConfirmationDialog
  isOpen={showExportCompleteChoice}
  title="Add a spotlight?"
  message={"A spotlight is a glowing highlight that follows your athlete. It is optional.\nEither way, your reel gets rendered next and you will watch it before it goes anywhere."}
  onClose={handleChoiceDismiss}      /* X and Escape, see semantics below */
  buttons={[
    { label: 'Finish without one', variant: 'secondary', onClick: handleFinishWithoutSpotlight },
    { label: 'Add a spotlight',    variant: 'cyan',      onClick: handleAddSpotlight, icon: Sparkles },
  ]}
/>
```

Notes on the choices above:

- **`variant="cyan"`, not `primary` (purple).** Cyan is the reel accent
  (`themeColors.js:21`), used by the "Ready to share" badge and the tile's publish CTA.
  Every "move my reel forward" action in this flow should be one color. Purple stays
  the generic app primary.
- **"Add a spotlight" matches the Overlay screen's own CTA text ("Add Spotlight",
  `OverlayModeView.jsx:40`),** so the card names the button the user is about to press.
  T8520's draft copy said "Add Overlay", which names a mode, not an outcome. T7700's
  decision about the Overlay screen's own button copy is untouched.
- Buttons render in DOM order left to right on desktop and, with the stacking fix,
  bottom to top on mobile (`flex-col-reverse`), so the primary is the LOWEST button on
  a phone (thumb reach) and the RIGHTMOST on desktop. This matches ConfirmationDialog's
  existing right-aligned primary convention.
- No `impressionKey`. This is a choice moment, not a frustration surface, and
  `recordUiImpression` counts blocked-user impressions (`ConfirmationDialog.jsx:34-49`).
- No em dashes in any string above (project rule).

### X / Escape semantics

T8520's file says "an X maps to the Skip action". Under D1 Option A, Skip starts a
render, and a render must never be triggered by a dismiss gesture.

**Under Option A:** X and Escape are a third, neutral outcome. They close the card and
leave the user on the Focus screen with the working video staged and the Overlay tab
enabled (`ModeSwitcher.jsx:68`). Nothing is lost, nothing is started. Title on the X:
"Not now".

**Under Option B:** X and Escape map to Skip exactly as the task file says.

### States

| State | Appearance |
|-------|------------|
| Default | Title, two-line body, two buttons, X in header |
| Hover (desktop) | Button variant hovers only (`hover:bg-cyan-500` / `hover:bg-gray-600`) |
| Focus | `focus:ring-2` from the Button base, ring offset `gray-900` |
| After either choice | Card unmounts immediately (`setShowExportCompleteChoice(false)`); the next surface owns feedback (overlay screen with render progress, or the Overlay editor) |
| Re-entry | The card is not re-shown for the same export; the double-fire guard `overlayTransitionFiredRef` (`ExportButtonContainer.jsx:185`) already ensures the completion handler runs once |

### Mobile (390x844)

Card width 358px, `px-6` body, buttons full width stacked with the primitive fix,
`min-h-11` guaranteed by `Button` size `md` (`py-2 text-sm` = 38px) plus the stacking
patch adding `min-h-[44px]` for coarse pointers. Vertical footprint approximately
header 57 + body 84 + footer 116 = 257px, centered, no scroll. Both CTAs in viewport,
which is the T8550 assertion.

### Test hooks

`data-testid="export-complete-choice"` on the dialog panel, and stable accessible
names on the two buttons (their labels). Unit assertions per T8520 step 4 stay valid:
completion sets the flag and does NOT change `editorMode`.

## 4. Surface 2: the draft preview player (T8530)

### 4.1 What it is

The SAME `CollectionPlayer`, mounted with a one-reel payload built from an unpublished
draft, plus two new optional props. The player stays strictly presentational: it never
learns what publishing is. All publish logic lives in a thin wrapper component.

```
DraftReelPreview (new, ~80 lines)          <- owns usePublishProject, builds the payload
  └── CollectionPlayer (existing)          <- gains onPublish / publishState / onShare props
```

Why a wrapper and not logic inside the player: `CollectionPlayer.jsx:13-21` states the
no-stores/no-fetching contract, and the public share viewer (`SharedCollectionView`)
and the diag harness both mount it. A store call inside it would break all three.

### 4.2 D2: where the wrapper is mounted and how it is opened

The surface must be reachable from two moments that live in different parts of the
tree, and it must survive the project disappearing from `projectsStore` (publish
archives the project, so `fetchProjects` drops it: `downloads.py:2193`,
`DraftTile.jsx:168`). A component that looked the project up live in the store would
unmount itself the moment publish succeeds.

**Option A (RECOMMENDED): a tiny ephemeral store + one mount in `App.jsx`.**

```js
// stores/reelPreviewStore.js  (ephemeral view state, never persisted)
{ payload: null, open(payload), close() }

// utils/finishedReelNav.js  (the shared helper T8520/T8530 co-own)
export function openFinishedReel(project) {
  useEditorStore.getState().goToProjectManager();   // no-op if already home
  useReelPreviewStore.getState().open(toDraftPlayerReel(project));
}
```

`App.jsx` renders `<DraftReelPreview />` once, next to the other top-level overlays.
`payload` is a SNAPSHOT taken at open time (`{ projectId, finalVideoId, name,
aspectRatio, clipCount, gameStartTime }`), exactly the pattern `DownloadsPanel` already
uses for `storyPlayer` (`DownloadsPanel.jsx:529-534`). This is not redundant state: the
snapshot outlives its source row by design.

- Pro: callable from anywhere without prop drilling, mirrors `galleryStore.open()`
  which `DraftTile.jsx:172` already calls from the publish handler.
- Pro: survives the post-publish `fetchProjects` drop.
- Con: one more small store.

**Option B: local state in `ProjectManager`.** Fails the "opened from the Focus screen"
case without a new prop chain, and `ProjectManager` is already large.

**Option C: local state in `App.jsx` plus a prop chain.** Same result as A with more
plumbing through `FocusScreen` and the export completion path.

### 4.3 Entry points (both call the same helper)

| Trigger | Path | Notes |
|---------|------|-------|
| Overlay export completes while the user is in the editor | `App.jsx:573-595` `handleExportComplete`, after `goToProjectManager()`, calls `openFinishedReel(project)` | This is the T8530 moment. The project must be re-read after `fetchProjects({force:true})` (line 574) so `final_video_id` is present |
| T8520's "Finish without one" (D1 Option A) | Reaches the SAME completion handler, because the render it fires is an overlay export | The helper is called from exactly one place. T8520's Skip does not call it directly, which removes the co-ownership risk the two task files worried about |
| T8520's Skip under D1 Option B | Would call `openFinishedReel` directly, but there is no final video, so the call cannot happen at all | Another argument for Option A |
| Overlay export completes while the user has navigated away | Unchanged: the existing `GlobalExportIndicator` toast announces it (`App.jsx:578-581`), no player is forced open | Correct: never yank a user out of another task |

The completion toast keeps firing (`GlobalExportIndicator.jsx:214-218`). Recommend
T8530 leaves that toast alone rather than adding a Publish action to it: the player is
now the publish surface, and a toast action plus a player CTA for the same gesture is
two primaries for one action.

### 4.4 D3: how the draft state is signaled

**Option A (RECOMMENDED): a one-line status strip between the header and the video.**

It carries the explanation the walkthrough proved is missing ("why is this not in my
reels?"), it is the natural home for the publish failure state (same slot, tint
change), and it disappears on publish, which makes the state change legible.

```jsx
{/* draft: cyan, calm, informational */}
<div
  data-testid="draft-preview-banner"
  className="flex items-center gap-2 px-3 py-1.5 border-y border-cyan-900/40 bg-cyan-950/30 text-cyan-200 text-xs"
>
  <EyeOff size={14} className="shrink-0" aria-hidden="true" />
  <span className="min-w-0">Only you can see this. Publish it to get a share link.</span>
</div>
```

**Option B: a badge chip next to the title** (`<span className="... bg-black/60
text-cyan-300 text-[10px]">Draft</span>`). Cheapest and most minimal-chrome, but at
390px it competes with the title for the ~110px the toolbar leaves, and it explains
nothing.

**Option C: an overlay chip on the video's top-left corner.** Keeps chrome out of the
layout, but text over video needs a scrim (style guide anti-pattern table) and it
collides with the per-reel title overlay animation at `CollectionPlayer.jsx:397-407`.

Recommendation A, with the copy above. Alternative wording if "Only you can see this"
reads too much like a privacy claim: "Not shared yet. Publish it to get a link."

### 4.5 Toolbar

One PRIMARY SLOT, first item in the right-hand cluster, mutually exclusive between
states. This is the slot the user's decision describes ("Publish is the toolbar's
primary action there, in place of where Share would go once published").

| Slot | Draft state | Published state (T8540) |
|------|-------------|-------------------------|
| 1 primary | **Publish** (`variant="cyan"`, `size="sm"`, icon `FolderInput`, label "Publish", `title`/`aria-label` "Publish to Highlight Reels") | **Share** (`variant="cyan"`, labeled, per T8540) |
| 2 | Edit (ghost, iconOnly, `Pencil`, title "Keep editing") | Download (ghost, iconOnly, `Download`) |
| 3 | Close (ghost, iconOnly, `X`, `aria-label="Close"`) | Close |

Deliberate omissions in the draft state:

- **No Download.** Drafts are not downloadable anywhere else in the app today
  (`DraftTile`'s kebab offers Rename / Open in Focus / Open in Overlay / Hide / Delete,
  `DraftTile.jsx:459-491`; Download exists only on published `ReelTile`). Adding it
  here would be a new capability smuggled in by a layout task, and it costs the 52px
  that keeps the title readable at 390px.
- **No Re-rank.** Ranking operates on published reels (`CollectionPlayer.jsx:334-346`
  gates on the reel being a published single-clip reel).
- **Edit** is the draft-state analogue of Re-edit and needs NO archive restore (the
  project is still live). It closes the player and opens the project at its furthest
  stage, the same rule `DraftTile.handleCardClick` uses (`DraftTile.jsx:304-314`).
  After publish the project is archived, so Edit is dropped: the restore-capable
  Re-edit already lives in the Highlight Reels drawer's player.

Prop contract added to `CollectionPlayer` (both optional, both render-gated exactly
like every existing toolbar prop):

```
@param {Function=} onPublish        - () => void; renders the Publish button when set
@param {boolean=}  publishLoading   - spins + disables Publish
@param {Function=} onShare          - (activeReel) => void; renders the Share button when set (T8540)
@param {boolean=}  shareLoading
@param {ReactNode=} statusBanner    - optional row rendered between header and video
```

`statusBanner` as a slot (rather than a `isDraft` boolean plus copy inside the player)
keeps the player free of product vocabulary and lets the wrapper own the draft/failure
tint swap.

**Coordination with T8540 (important).** T8540 is WIP and adds `onShare` to the same
toolbar. To make the two land in either order without a stranded state, whichever lands
FIRST should introduce the primary slot and the `onShare` prop contract. If T8530 lands
first, it wires `onShare` in its own wrapper using `useWebShare` (`hooks/useWebShare.js`,
coarse pointer = native share sheet, fine pointer = copy link plus "Link copied" toast),
which is exactly the split T8540 specifies and is about 15 lines. T8540 then only adds
the `DownloadsPanel` and `ReelTile` wiring. If T8540 lands first, T8530 passes the prop
and adds nothing.

### 4.6 Publish interaction

The gesture is the click. `usePublishProject(project)` (T8530 step 2) carries the whole
T4050 contract verbatim out of `DraftTile.jsx:127-180`, including the pieces easy to
lose in an extraction: `useGalleryStore.fetchCount({force:true})`,
`notifyCollectionsChanged()`, `fetchProjects({force:true})` (never optimistic removal),
`useQuestStore.recordAchievement('moved_to_my_reels')`, and the `[Publish]` console
tracing that makes a real attempt correlatable with the backend `[SYNC]` line.

From the player, call it with `openGallery: false`. Opening the Highlight Reels drawer
behind a fullscreen player is invisible noise; `DraftTile` keeps `openGallery: true`.

| Phase | Player appearance |
|-------|-------------------|
| Idle (draft) | Cyan banner, Publish enabled |
| Publishing | Publish shows `Loader` and is disabled (`Button loading`); banner text swaps to "Publishing..." with no icon change; Close STAYS enabled (the hook must be unmount safe: side effects go through `getState()` calls, only `setState` needs a mounted guard) |
| Success | Banner unmounts; primary slot swaps Publish to Share; Download appears; toast.success "Published" with message "Anyone with the link can watch it." The Share button gets a one-shot attention ring for 1.5s so the swap is noticed: `ring-2 ring-cyan-400/70 animate-pulse` removed on a timer or on first interaction |
| 503 `sync_failed` | Banner turns amber and becomes the retry surface, in place: `bg-amber-950/30 border-y border-amber-900/40 text-amber-200` with `AlertTriangle` icon, text "Couldn't save to the cloud." and an inline Retry button (`variant="outline"`, `size="sm"`, amber text) re-running the SAME gesture args. Publish button stays visible but disabled while retry state is set. Copy matches `DraftTile.jsx:849` exactly so the two surfaces read as one system |
| Generic failure | `toast.error('Could not publish', { message })` plus the same amber banner with Retry. This replaces the `alert()` at `DraftTile.jsx:174-177` on BOTH call sites |
| Closed mid-failure | Nothing is stranded: the draft was never optimistically removed, so the tile is still on the board with its own Retry (`DraftTile.jsx:846-859`). The error toast should say where: "Your reel is still in Clips. You can retry from there." |

Reachability of the T4050 contract is therefore satisfied twice: in place inside the
player, and on the board after closing.

### 4.7 Post-publish coherence

The transition is unusually clean because the identity does not change: publish sets
`published_at` on the SAME `final_videos` row (`downloads.py:2146-2156`) and returns
that same `final_video_id` (`:2215`). So the stream URL, the poster, the reel name and
the player instance all stay identical. Nothing reloads, the video does not restart.
Exactly three things change: the banner disappears, the primary slot swaps, and
Download appears. That is the "not jarring" property the task asked to confirm.

One caveat worth stating in the design doc: sharing is not technically gated on
publishing (`routers/shares.py:475-514` does not check `published_at`), so the
Publish-then-Share ordering is a product decision, not a constraint. It is the right
one: publish is what freezes the display name (`downloads.py:2135-2149`, the
explicit-names-after-archive rule) and what puts the reel where its owner can find it
again. A shared-but-unpublished reel would be a link to something absent from the
owner's own Highlight Reels.

### 4.8 Mobile (390x844)

Header is `px-3 py-2` (366px of content) with `gap-2`.

| State | Cluster width | Title gets |
|-------|---------------|------------|
| Draft | Publish labeled (~96) + Edit 44 + Close 44 + 2 gaps (16) = 200 | ~158px |
| Published | Share labeled (~90) + Download 44 + Close 44 + 16 = 194 | ~164px |

Both leave a readable truncated title. For contrast, keeping today's labeled Download
plus Re-edit plus Re-rank alongside a labeled primary would consume ~360 of 366px and
crush the title to nothing, which is the concrete reason for the omissions in 4.5.

Vertical stack: scrubber (~16) + header (~52) + banner (~34) + video `flex-1`. All
chrome is above the fold by construction, so the T8550 assertion ("primary CTA visible
without scrolling at 390x844") holds structurally, not by luck.

Touch targets: `Button size="sm" iconOnly` already floors at 44px on coarse pointers
(`Button.jsx:117`). The labeled primary at `py-1.5 text-sm` is 34px tall, BELOW the
44px floor. Add `coarse-pointer:min-h-11` to the primary slot button. This is a real
gap in the current player (today's labeled Download has the same 34px height) and is

## 8. Style guide additions (only after approval + implementation)

If approved, add to `.claude/references/ui-style-guide.md`:

1. **Player status strip** pattern: a full-width one-line row between a fullscreen
   player's header and its video, cyan for informational state, amber for a retryable
   failure, replacing itself in place rather than stacking a second surface.
2. **Primary action slot** convention for the player toolbar: exactly one labeled,
   accent-colored action, first in the right cluster, state-exclusive; everything else
   is icon-only ghost; Close is always last.
3. **Dialog footer stacking**: `flex-col-reverse` below `sm`, buttons `w-full`, so two
   labeled actions never overflow a 390px viewport.
