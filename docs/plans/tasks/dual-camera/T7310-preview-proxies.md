## Problem

A pool game can carry many full-length high-bitrate cameras. Annotate switching between
lanes (§6) streams whichever feed is active; with several 4K+ sources that may feel heavy
(bandwidth, seek latency, decode). The dual-asset answer is settled in
[UX-SPEC.md §5b item 3](UX-SPEC.md): **low-res in Annotate, full-res in Framing** — but
whether generated proxies are actually needed is an empirical question.

**Gate: this task starts only when real multi-feed pools demonstrably feel slow** (user
reports or measured seek/switch latency on staging pools). File the evidence in this
task's Progress Log before classification.

## Solution

1. **480p preview renditions** generated by the **mov-atom probe Modal job** (the same
   app that computes ALIGNMENT.md's per-source artifacts — one Modal touch per source,
   probe + proxy in one pass), stored beside the source **keyed by blake3** (e.g.
   `games/{blake3}_preview.mp4` — exact key at design; content-addressed like the source,
   so every account referencing the source shares one proxy).
2. **Consumption split:** Annotate and all preview surfaces (tiles, pickers, §7 line-up
   players) stream the proxy when one exists; **Framing and export ALWAYS resolve the
   full-res master** (`resolve_clip_source` — clips are pointers, extraction reads the
   source; already the architecture). No user-facing toggle — it is simply how high-res
   games stay light.
3. **`.LRF` shipped proxies** detected at T5495's folder upload (DJI ships them beside
   the masters) fill the SAME rendition slot — a shipped proxy means no generation cost;
   the quiet confirm line ("Preview files detected — fast editing enabled") is §5b's.
4. **Absence is fine:** no proxy → stream the master, exactly today's behavior. Proxy
   generation failure never blocks anything; it logs and the source plays full-res.
